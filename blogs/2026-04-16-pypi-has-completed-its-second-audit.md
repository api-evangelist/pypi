<p>In 2023 <a href="../2023-11-14-1-pypi-completes-first-security-audit/">PyPI completed its first security audit</a>, and I am proud to announce that we have now completed our second external security audit.</p> <p>This work was funded by the <a href="https://www.sovereign.tech/">Sovereign Tech Agency</a>, a supporter of Open Source security-related improvements, partnering with <a href="https://www.trailofbits.com/">Trail of Bits</a> to perform the audit. Thanks to ongoing support from <a href="https://alpha-omega.dev/">Alpha-Omega</a>, my role at the PSF enabled me to focus on rapid remediation of the findings.</p> <p>This time around, there's no three-part series, as the scope was narrower, focused only on PyPI's codebase and behaviors. on first, and which ones to accept for now.</p> <p>There were 2 High, 1 Medium, 7 Low, and 4 Informational severity findings.</p> <p>All but 2 findings have been remediated, and the remaining 2 are accepted for now. More details on the accepted findings below, but in general these were accepted because they require significant effort to remediate, and the risk they pose is relatively low.</p> <p>To reiterate, the <a href="https://github.com/trailofbits/publications/blob/master/reviews/2026-04-pypi-warehouse-securityreview.pdf">published report PDF</a> goes into deeper detail about each finding, so I recommend reading that for the fullest context first.</p> <h2 id="details">Details</h2> <p>For some of the Remediated entries and all the Accepted ones, I'll go into more detail below.</p> <h3 id="tob-pypi26-1-oidc-jti-anti-replay-lock-expires-before-jwt-leeway-window-closes">TOB-PYPI26-1: OIDC JTI anti-replay lock expires before JWT leeway window closes</h3> <p>PyPI's <a href="https://docs.pypi.org/trusted-publishers/">Trusted Publishing</a> flow uses OIDC JWTs issued by CI providers to mint short-lived upload tokens. Each JWT contains a <code>jti</code> (JWT Token Identifier) claim that should be single-use. To enforce this, we store each <code>jti</code> in cache (Redis) with an expiration of <code>exp + 5</code> seconds, and check whether it already exists before accepting a new token.</p> <p>The problem: <code>PyJWT</code> is configured with <code>leeway=30</code>, meaning it accepts tokens up to 30 seconds past their <code>exp</code> claim. This created a 25-second window (from <code>exp + 5</code> to <code>exp + 30</code>) where the cache key had already been evicted, but the JWT still passed signature verification. During that window, a replayed token would pass both the signature check and the <code>jti</code> uniqueness check.</p> <p>The fix was straightforward -- align the cache TTL to outlive the full leeway window by <a href="https://github.com/pypi/warehouse/pull/19627/changes#diff-b6993869ec628f626827f05a87938a08f1ced03e52b68a49000100910d9d46f2R288">setting the expiration to <code>exp + leeway + margin</code></a>. I also took the opportunity to centralize these time-window constants so they're derived from a shared configuration, preventing future drift when one value is updated without the other.</p> <h3 id="tob-pypi26-6-ip-ban-bypass-via-macaroon-api-token-authentication">TOB-PYPI26-6: IP ban bypass via macaroon API token authentication</h3> <p><strong>Accepted for now.</strong></p> <p>PyPI administrators can ban IP addresses through the admin dashboard. The session authentication policy enforces this by checking the IP against the ban list before returning an identity. However, the macaroon (API token) authentication policy doesn't perform this same check. This means a user with a valid API token could continue uploading packages from a banned IP address.</p> <p>I've accepted this finding for now. IP bans are a relatively blunt tool that we use sparingly, <a href="https://github.com/pypi/warehouse/pull/19213">introduced late last year</a> to mitigate a specific wave of abuse. The practical risk here is low - if we've identified a malicious actor, we have other mechanisms to disable their account entirely. That said, it's a gap worth closing, and we'll likely address it as part of broader work on making security controls consistent across all authentication methods.</p> <h3 id="tob-pypi26-8-organization-members-can-invite-new-owners-due-to-a-missing-manage-permission-check">TOB-PYPI26-8: Organization members can invite new owners due to a missing manage permission check</h3> <p>This was the highest-severity finding in the audit, and one I prioritized immediately.</p> <p>The <code>manage_organization_roles</code> view handled both <code>GET</code> (viewing the people page) and <code>POST</code> (sending invitations) under a single <code>@view_config</code> decorator that only required <code>OrganizationsRead</code> permission. This meant any organization member could send invitations with <em>any</em> role - including Owner - to any PyPI user.</p> <p>The irony is that we already had the correct pattern elsewhere in the codebase. Views like <code>resend_organization_invitation</code> and <code>change_organization_role</code> correctly use separate <code>@view_config</code> decorators for <code>GET</code> and <code>POST</code> with distinct permission requirements. This one was simply missed.</p> <p>The <a href="https://github.com/pypi/warehouse/pull/19610">fix was to split the view configuration</a>: <code>GET</code> requires <code>OrganizationsRead</code>, <code>POST</code> requires <code>OrganizationsManage</code>. As part of the audit, Trail of Bits also developed a custom CodeQL query to detect this class of issue - views that handle state-changing <code>POST</code> requests under a read-only permission check. I'll integrate that into our CI to catch this pattern going forward.</p> <h3 id="tob-pypi26-10-wheel-metadata-is-served-to-installers-without-validation-against-upload-metadata">TOB-PYPI26-10: Wheel METADATA is served to installers without validation against upload metadata</h3> <p><strong>Accepted for now.</strong></p> <p>This is a nuanced one. When a wheel is uploaded to PyPI, we store two independent sources of metadata: the form-declared metadata from the upload request (which populates the database and the JSON API), and the embedded <code>.dist-info/METADATA</code> file extracted from the wheel itself (which is served via <a href="https://peps.python.org/pep-0658/">PEP 658</a> to <code>pip</code> for dependency resolution).</p> <p>These two sources are never compared. In theory, an attacker could embed hidden dependencies in the wheel's <code>METADATA</code> that <code>pip</code> would install, but that security tools querying the JSON API would never see.</p> <p>We've accepted this for now because the fix is non-trivial. Properly validating embedded metadata against upload metadata touches a core part of how we handle uploads, and requires careful consideration of edge cases across the ecosystem. This is something we want to get right rather than rush, and <a href="https://github.com/pypi/warehouse/issues/8090">involves a fair amount of database changes, including data backfills</a>.</p> <h3 id="tob-pypi26-13-organization-scoped-project-associations-persist-after-project-transfer-or-removal">TOB-PYPI26-13: Organization-scoped project associations persist after project transfer or removal</h3> <p>This was the other High-severity finding, and a subtle one.</p> <p>When a project is transferred between organizations, the <code>OrganizationProject</code> junction record is correctly deleted and recreated. However, the <code>TeamProjectRole</code> records - which grant a team's members access to specific projects - were <em>not</em> cleaned up during the transfer.</p> <p>This meant that if LexCorp Organization had a "release-engineers" team with Owner-level access to a project, and that project was transferred to Organization OsCorp, the LexCorp team's members would silently retain full access to the project. Worse, the receiving organization had no visibility into these stale associations - team-granted permissions are resolved at ACL evaluation time and don't appear as individual collaborator entries in the UI.</p> <p>The fix in <a href="https://github.com/pypi/warehouse/pull/19749">pypi/warehouse#19749</a> ensures that <code>TeamProjectRole</code> records belonging to the departing organization are cleaned up when a project is transferred. Auditing database records proved that this has not happened in the past, so I am confident there have been no such transfers with dangling permissions. I also added defensive filters in the project's ACL computation to verify that a team's organization matches the project's current organization before granting permissions, so stale records can't grant access regardless of how they're orphaned.</p> <h2 id="summary">Summary</h2> <p>Working with <a href="https://www.trailofbits.com/">Trail of Bits</a> was again a pleasure. The team were thorough, communicative, and clearly understood the nuances of a system like PyPI - where the threat model spans everything from CI/CD token replay to metadata integrity for millions of downstream users.</p> <p>Beyond the 14 findings, the audit also produced proposal reviews for features I'm considering (per-org Trusted Publishers, TOTP hardening, and more), as well as custom CodeQL queries to integrate into our CI/CD pipeline.</p> <p>This audit was funded in partnership with the <a href="https://www.sovereign.tech/">Sovereign Tech Agency</a>, which continues to support security improvements across the Open Source ecosystem.</p> <p>My work at the Python Software Foundation is supported by <a href="https://alpha-omega.dev/">Alpha-Omega</a>.</p>
